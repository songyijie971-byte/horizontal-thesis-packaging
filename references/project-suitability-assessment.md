# 项目论文转化适配度评估

## 目标

先判断横向项目是否值得作为硕士论文主线。不要默认把所有项目包装成论文；小横向、纯交付、缺少本人工作量或无法验证的项目，要明确提示风险并给替代路线。

## 评分维度

每项 0 到 2 分：

- 0 分：明显不足，当前不能支撑论文表达。
- 1 分：有基础，但需要补材料或收窄口径。
- 2 分：比较充分，可以支撑论文蓝图。

| 维度 | 2 分表现 | 1 分表现 | 0 分风险 |
| --- | --- | --- | --- |
| 项目规模 | 有完整业务流程、多个模块、持续迭代或真实场景 | 有几个模块，但链路不完整 | 只有小页面、小脚本、小接口、一次性维护 |
| 技术问题 | 能抽象出效率、准确率、稳定性、实时性、集成度、可维护性等问题 | 有痛点，但还停留在业务描述 | 只有“做了一个系统”，没有明确技术痛点 |
| 本人工作量 | 本人负责核心模块、算法、架构、实验、部署或联调 | 本人负责局部模块，但边界还不清 | 只参与配置、页面修改、文档整理或边缘任务 |
| 数据/场景 | 有真实数据、日志、公开数据、仿真场景、企业案例或测试样例 | 有截图、样例或少量测试材料 | 没有数据，也无法构造可信验证场景 |
| 验证可能性 | 能补功能测试、性能测试、对比实验、消融实验或场景验证 | 能补部分测试，但指标不完整 | 只能展示截图，无法量化验证 |
| 方法含量 | 有算法、流程优化、系统架构、集成机制、数据处理或工程优化点 | 有工程设计点，但方法表达较弱 | 只是常规 CRUD、权限管理、报表展示 |
| 保密风险 | 能脱敏描述场景、数据和企业信息 | 能脱敏部分内容，但关键证据受限 | 关键材料不能公开，且脱敏后无法说明价值 |
| 时间成本 | 剩余时间足够补证据和整理材料 | 时间偏紧，只能补关键证据 | 时间太紧，只能靠话术包装 |

| 总分 | 建议结论 | 说明 |
| --- | --- | --- |
| 13-16 | A 类 | 适合单独转论文 |

## 判断置信度

适配度结论必须标注置信度，避免把信息不足误说成确定判断。

| 置信度 | 使用条件 | 输出策略 |
| --- | --- | --- |
| 高 | 8 项中至少 6 项有明确依据，且本人工作量、验证可能性、保密风险都能判断 | 可以给 A/B/C/D 结论和完整蓝图 |
| 中 | 8 项中有 4-5 项有依据，关键证据有缺口但能初步判断 | 给临时结论，列出最该补的 3 个材料 |
| 低 | 只有一句项目简介、只有截图/代码目录，或本人工作量、数据、验证方式不清 | 不做强结论，先用最小输入表追问，再给保守初判 |

推荐句式：

```text
判断置信度：中。
原因：目前能确认项目场景、本人负责模块和部分系统成果，但数据来源、实验指标和保密边界还不清。
```

## 结论分档

### A 类：适合单独转论文

项目有明确场景、技术问题、本人工作量和可验证证据。直接进入论文转化蓝图，输出题目、研究问题、章节映射、证据台账和实验补全清单。

### B 类：可以转，但需要补材料

项目有论文潜力，但目前缺少实验、数据、本人贡献说明或研究问题。可以生成蓝图，但必须标出“先补什么证据，否则不建议写成结论”。

### C 类：不建议单独转论文

项目太小、太偏交付、技术含量不足或证据不足。建议先在单项目内部补核心模块、测试证据、数据场景或技术问题；如果补不起来，再作为其他论文的模块、案例或应用验证。

### D 类：不建议转论文

缺少本人工作量、无法脱敏、无法验证、只有普通业务开发或临时维护任务。不要硬转；建议换题、重新争取更核心模块，或寻找一个更可验证的研究主线。

## 替代路线

当项目是 C 类或 D 类时，优先给出以下出路：

1. 先在当前单项目内部寻找可验证的局部技术问题，例如性能优化、数据处理、调度策略、异常检测或检索评估。
2. 争取接触更核心的模块、数据流、测试记录或部署材料。
3. 补实验，把交付成果变成可证明的论文证据。
4. 把当前项目降级为应用案例、模块或实践材料。
5. 放弃该项目作为主论文，仅作为实习、项目经历或辅助材料。
6. 只有当用户明确有其他相关项目时，才建议合并多个项目形成更完整主线。

## 输出句式

```text
结论：B 类，可以转，但必须补证据。

8 项评分：10/16。

判断置信度：中。

理由：
- 项目有真实应用场景；
- 本人负责模块可以形成工作量说明；
- 但目前研究问题不够清楚；
- 缺少可量化实验。

建议路线：
- 不要直接写成“某系统设计与实现”；
- 改成“面向某场景的某方法/系统研究与实现”；
- 先补 3 类证据：功能测试、性能测试、场景案例对比。
```
